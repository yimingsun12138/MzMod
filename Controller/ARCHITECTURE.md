# From a player choice to a game file

One application of the settings takes a region and a saved set of choices and produces a complete `MzMod.mpq/` directory. The same inputs can be rendered in memory through `render_mod(region, &settings)`. The installer commits that result to disk together with its settings and file fingerprints.

| Responsibility | Input | Output |
| --- | --- | --- |
| [Cargo build](build.rs) | Public game resources, default choices, README and UI assets | A standalone executable with both regions, typed defaults, visual selection rules, regional preview records and equipment colors |
| [Package metadata](build_support/package_metadata.rs) | Each client’s native manifest and build marker, plus the Cargo author | A verified mod name, save location and author for the archived package, and build numbers for the installer and About page |
| [Output path ownership](build_support/output_paths.rs) | Regional archives and the files each renderer controls | A per-region check that every controlled game path has one owner and a usable Windows destination |
| [Page definitions](src/ui/options.rs) | Player input and the current draft | Edits to the choices owned by a page, including restoring its defaults |
| [Settings](src/settings.rs) | Saved choices, draft edits and [compiled prerequisites](build_support/prerequisites.rs) | Merged choices for persistence and effective choices for rendering |
| [Editing session](src/ui/session.rs) | Edits, destination profile and installer result | A draft for each region, an output path and the current status for the window |
| [Region](src/region.rs) and [regional template](src/template.rs) | Shared resources and the selected region | The same game-relative paths during catalog compilation and extraction, for both the main template and optional jewel icons |
| [Item catalog compiler](build_support/item_validation.rs) | The [item catalog](../ModTemplate/items.json), both regions' game resources and optional jewel icons | The validated catalog bytes embedded in the executable |
| [Item renderer](src/items.rs) | Selected item options and the embedded catalog | Localized names, tooltip colors, inventory icons and ground models |
| [Visual renderer](src/visuals.rs) | Selected visual options and the [visual catalog](../ModTemplate/visuals.json) | Enabled scene and interface overrides and a composed missile table |
| [Existing installation](src/install/existing.rs) | Native mod identity, build marker and optional controller profile | Common evidence for portable routing, explicit installation and recovery |
| [Installation profile](src/install/profile.rs) | Persisted choices, format and file fingerprints | Migrated player choices and retained extension fields for the next update |
| [Release fingerprints](build_support/release_fingerprints.rs) | The bytes archived for each region and its previous release fingerprints | A compiled list of package-relative paths and SHA-256 values that the installer recognizes |
| [Installer](src/install.rs) | Rendered files, verified profile and destination | An installation with player-owned files preserved and updated fingerprints |

The [native JSON check](build_support/game_json.rs) validates game resources before archiving their original bytes. Each JSON object has unique field names. A high-precision coordinate can pass through unchanged, while an invalid number or repeated coordinate stops compilation with the resource path.

## Extending a feature

Start with the player's decision and an adjacent case that must behave independently. A beam on a magic small charm and a beam on Annihilus have separate choices. An inventory sprite and a ground model belong to different renderers even when they depict the same item.

- Change a default in [defaults.json](../ModTemplate/defaults.json). The [settings compiler](build_support/settings.rs) reads each field once and checks that each visual option and prerequisite refers to a single toggle. Rust checks the resulting initializer against the saved settings type, including the length of the rune selection. Rebuild the executable to distribute the new default. Installed profiles retain the player's saved choices.
- A whole-file override has one owner per region. The item and visual compilers register the actual paths they read, edit, add or withdraw for player settings. Installation metadata also has a reserved path. For example, assigning the Ber inventory sprite to waypoints in CN conflicts with the rune icon setting in that client. Multiple jewel models may request the same sprite from the jewel renderer. Generated files require a free destination, including every directory in their path.
- In `visuals.json`, the owner's `paths` list applies to both clients. Use `regional_paths` for additional game paths controlled by that setting in `INT` or `CN`. For example, a new waypoint unique to the international client belongs in `waypoints.regional_paths.INT`. At runtime the visual renderer uses the path list compiled for the selected client.
- A setting can declare its prerequisites under `requires` in `visuals.json`, including a setting whose files are managed by the item renderer. The compiler resolves the full chain for each dependent setting. The window uses those rules to enable its controls. Previews and both game renderers use the same effective settings. For example, switching off the mini cube suspends automatic opening. Switching the cube back on restores the player's saved choice.
- Edit the regional [desktop entry HUD](../ModTemplate/common/data/global/ui/layouts/hudpanelhd.json) or [gamepad entry HUD](../ModTemplate/common/data/global/ui/layouts/controller/hudpanelhd.json) to change a control. The [HUD compiler](build_support/cube_hud.rs) reads the entry, startup and gameplay panel names from [cube-hud.json](../ModTemplate/cube-hud.json). It derives the desktop gameplay HUD by removing the timer that opens the startup panel. The gamepad gameplay HUD inherits the resulting desktop layout and retains the gamepad controls. For example, moving the gamepad cube button updates its position before and after automatic opening. With automatic opening disabled, the manual gamepad button remains on the entry HUD. The [layout compiler](build_support/cube_layout.rs) checks the startup panel against its timer delays. It must close the entry HUD, open the gameplay HUD, open the cube, close the inventory and unload itself, in that order. Reordering widgets in the JSON keeps that behavior when their delays are preserved. The [control check](build_support/cube_controls.rs) verifies the clickable entry, close action and cube inventory grid. A decorative image carrying the same message cannot serve as a button. Cargo archives and fingerprints the resulting layouts with the other game files.
- Cargo and the renderer read the same [item catalog schema](src/item_catalog.rs). Each rune declares its game number, both display names and a distinct ground model route. The [rune catalog reader](src/rune_catalog.rs) places the record in its saved selection slot, so reordering records keeps #30 bound to Ber. Each rune has a standard and a low-end numbered inventory sprite. Annihilus and Hellfire Torch use both variants for their permanent inventory appearance. For a model with `numbered_inventory_variants`, the jewel renderer installs the unnumbered look and every numbered look in both sprite resolutions from the selected region. A count of zero selects the unnumbered pair. An explicit `icons` list can supply additional shared sprites or serve as the model's entire inventory declaration.
- Each combat setting owns specific keys in the shared missile table. Its `native_missiles` entry maps each key to its original effect. Use a string when both clients use the same effect, or an object with an `INT` and a `CN` string when their effects differ. With both settings enabled, the renderer emits the region's enhanced table. With both disabled, the game supplies its native table. With only assassin eye care enabled, the renderer restores the four Thunder Storm routes for the selected client and withdraws the sorceress cast overlay. Enabling only Thunder Storm restores the ten assassin routes and keeps the cast overlay.
- The [ground model catalog](src/ground_model.rs) associates each route with its item selection and the source of its appearance. The [drop renderer](src/items/beams.rs) reads that selection. Enabling El adds the beam to a copy of the native model. Disabling Gul withdraws its beam-only override. Disabling Annihilus removes the beam from its private appearance. For each region, Cargo checks that the `normal`, `uber` and `ultra` slots of Annihilus and Hellfire Torch each point to their respective private model, with unique jewel beams on and off. A third unique item using either model would also acquire the charm's beam. The check reports the item and affected slot. Several jewel qualities can select the same jewel model.
- The [model check](build_support/ground_model_validation.rs) exercises the same [entity editor](src/ground_beam.rs) used by the renderer. Each optional native model must accept the beam and have its output path free in both regions. Each prelit regional model must contain exactly one complete catalog beam and each particle it declares. A particle shared with another entity keeps its dependency entry and metadata when the beam is removed. Scene and interface settings cannot claim a drop model as a whole-file override.
- Magic and rare jewels use the base item table's `asset` field. Unique jewels use the `normal`, `uber` and `ultra` fields in the unique item table. The shared [jewel route editor](src/jewel_routes.rs) reads the selected region's table and redirects only those fields on the declared items. A region without a base table uses the native copy in the item catalog. Cargo applies the same edit in memory for each table in each region before embedding the template. The [jewel renderer](src/items/jewels.rs) writes the enabled tables, installs their inventory sprites and returns the required model routes to the drop renderer. Rainbow Facet can therefore have a beam while a perfect diamond keeps its original appearance.
- For a new choice, define its persisted field in [Settings](src/settings.rs), its initial value in the defaults and its control on the owning page. Implement the observable change in the renderer that owns the resource. Check both switch states in both regions, including other choices that share the file.
- Address a localized name by its native bank, numeric id and case-sensitive `Key`. Each key at each level of this index is unique. Cargo reports a repeated identity or an unknown rule field when it reads the catalog. Embedded native game models and tables retain their client-defined fields. The [label renderer](src/items/labels.rs) takes a label rule, the player's six text choices and the source text for one locale. For example, the full name of rune #10 can include a gem ingredient. Its short name and the full name of rune #9 omit the ingredient. The [catalog check](build_support/label_validation.rs) applies the renderer to each declared record in both clients for every combination that edits text. The compiler also checks that the line bound to `english_name` in each Chinese translation reproduces the item's English name. Swapping Spirit's two roles while leaving its translations in place would wire the MAX switch to its English name. Compilation reports the affected region and string identity.
- For base tiers and armor weights, the regional item row determines which translations the renderer edits. A [suffix group](build_support/base_suffixes.rs) supplies the full, tier-only and weight-only endings used by all items that reference it across both clients. For example, turning off both choices changes the German Monarch from `[ms]Monarch [X]|[L]` to `[ms]Monarch`, preserving its grammatical prefix. Adding a translation to one regional row requires a matching suffix in its group. Other rows keep their own language fields.
- The [overlay source resolver](src/chinese_overlay.rs) scans the JSON banks directly under the selected client's string directory at build time. Each row in the Chinese overlay requests a source by numeric id and case-sensitive `Key`. An ambiguous request reports both source banks. Unrequested rows may share an identity, and requests without a source retain their regional text. If a setting can change a source's `zhTW`, every matching overlay row must have a string in `zhCN`.
- The [bank writer](src/items/string_banks.rs) uses the compiled source list for the selected region. When an item's Traditional Chinese text changes, the writer copies that text into each matching overlay row's `zhCN` field. Other fields, including regional notes on duplicate target rows, keep their original values. Each [preview specimen](assets/ui/preview-items.json) must supply both [preview languages](src/preview_items.rs) in each client. The preview uses the same label renderer as the bank writer.
- The [preview compiler](build_support/previews.rs) reads each region's HD profile. Plain base items use `TooltipStyle.DefaultColor`, runes use `RuneColor`, and the runeword example uses the profile's gold font color. For inline colors, the compiler maps the supported game codes to named profile colors. The [tooltip painter](src/ui/previews.rs) applies each recognized code from that position to the end of the line or the next code. It centers and scales the entire line as one unit. For example, an explicit orange rune name keeps its orange span when the region changes its default rune color.
- To change which rune appears on the left or right, edit the corresponding entry in [preview-items.json](assets/ui/preview-items.json). For each region, Cargo resolves the entry's bank, id and Key to a rune number and its inventory route. It pairs the native sprite in [native-rune-icons](assets/ui/native-rune-icons) with the standard numbered sprite at that route in the game template. The numbering switch selects which image the window displays. A CN-only change to Ber's numbered sprite therefore appears when previewing that choice in CN. When introducing another rune, supply its native sprite for both regions using the same `common`, `INT` and `CN` layout as the game template.
- The [equipment-name color switch](src/item_colors.rs) owns the `EtherealColor` and `SocketedColor` bindings within `TooltipStyle`. Profile-wide colors are available to every layout in either switch state. For example, a mercenary panel can reuse the socketed color while equipment names use the native gray. The item catalog records each native RGBA value and its original reference, where present. If the reference still resolves to that value, the renderer restores it. Otherwise it writes the native RGBA directly into the tooltip field. The [preview compiler](build_support/previews.rs) applies the same operation to each region's profile.

Each output path has one source in `common/` or the chosen regional tree. Preserve native field names, lookup keys and messages. Existing profile field names are part of the installation format. Run `cargo test --locked` from this directory. On Windows the suite also exercises the native UI. For the Windows x64 GNU LLVM release target, the linker writes a zero PE timestamp. With identical toolchains, dependencies, build flags and remapped checkout paths, separate builds can be compared byte for byte.

## Updating an installation

[Location preferences](src/ui/session/locations.rs) track the last selected region and one game directory per region. Selecting a region changes that preference and reads its latest directory. Selecting a directory or returning to portable export updates only that region's path. Each window reads and updates the file under one lock, so edits to different regions survive concurrent use.

Each regional draft holds its displayed destination, the profile loaded there and the player's edits. Apply sends that destination to the installer, which locks it, verifies its identity and merges the edited choices into its latest profile. If another window has since installed the other region at the displayed path, the edits remain in the draft. Selecting the default location again resolves and displays the available regional path for the next Apply. For example, editing the beam for rune #9 preserves an edit to rune #30 saved by another window. The installer renders the merged choices and writes the game files and profile in one transaction. After a successful commit the window adopts the settings that were written. A failed apply keeps the draft available for retry. Callers supplying an entire replacement profile can use `Destination::apply`.

The template compiler resolves each region's native build marker through the same resource index it uses to package the game files. Portable routing checks the same native MzMod identity, build marker and optional profile as an explicit installation. For example, when a different mod beside the executable carries the CN build number, the controller can still reopen the MzMod under `CN/MzMod/`. A managed package must have a readable, supported profile consistent with its client build. A legacy package can identify its region automatically when its build number is unique to that region. When both regions share a build number, a fresh portable export uses a regional subdirectory beside the existing package. Before writing, the installer inspects the selected directory under the installation lock. An empty directory accepts a fresh installation. If the regional subdirectory belongs to the other client, an available shared destination can receive the new installation. A legacy package can be adopted when its native build matches the selected region. A controller-managed package also has a saved profile identifying its region and the files it installed. An older build can be upgraded when its saved build-marker fingerprint matches.

A format-1 profile has one value per setting. Earlier profiles stored the seven tomb symbols under the entrance choice. When `tomb_symbols` is absent, the reader uses the saved value of `entrances`. An explicit tomb-symbol choice takes precedence. New installations use the current template defaults. The [profile field reader](src/install/profile/fields.rs) recognizes the fields declared by each saved record. Updating a choice copies the original JSON values of additional fields in the profile and its settings object, including large integers and precise decimals.

The [fingerprint reader](src/file_fingerprints.rs) checks saved and historical manifests against Windows path rules. Each file has one path and one SHA-256 digest. Letter case in the digest and the spelling of a Windows path can vary between releases. A controller-created profile also records `modinfo.json` and the game build marker.

On update, [file ownership](src/install/ownership.rs) combines the region's release fingerprints with those of the installed profile and the newly rendered output. For example, a v0.1.0 book stand with its original digest can be replaced. A player-edited font occupying a managed path stops the update even when the player has switched the font off. The installer lists all detected ownership conflicts, including a player file occupying a required directory. File-access errors identify the affected path so the same draft can be retried. Additional files outside those paths are copied into the replacement.

If an update was interrupted after moving the live directory aside, the transaction restores the previous directory. When both directories exist, [payload verification](src/install/payload.rs) checks every file recorded in the live profile, including the mod identity and client build marker. Missing files, changed bytes or ambiguous paths leave both directories in place and identify the problem in the controller. A complete installation can release the backup with additional player files present. Recovery uses the installed version's own fingerprints so older managed profiles can be verified before an upgrade.
